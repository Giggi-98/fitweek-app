## Problemi, in ordine di priorità

### Alta
1. **Progressioni errate nel seed** (verificate per coordinate di colonna nel PDF):
   - `b6` Curl manubri su panca: PDF 4 serie da **W5**; seed da W4.
   - `c5` Calf su rialzo: PDF 6 serie da **W7**; seed da W6.
   Le routine stanno nello stato JSON: serve una migrazione dati, non solo la correzione di `seed.py`.
2. **Allenamento salvato solo a fine seduta**, bozza solo in memoria: ricarica, chiusura scheda o kill del browser su telefono durante 2,5 h di palestra = perdita dei dati. Data, durata e note si perdono anche cambiando settimana/giorno.
3. **Nessun backup automatico** del DB; solo export JSON manuale.
4. **Repository git**: radice in `/opt`, nessun commit, contiene altri progetti; un `git add .` includerebbe `.env`. Nessun `.gitignore`.
5. **Volume dipendente dal nome directory**: `fitweek-app_fitweek_data` deriva dal project name di compose. Rinominare la cartella o usare `-p` diverso crea un volume vuoto (dati "spariti"). Oggi il DB è ancora il seed: è il momento più economico per correggere.

### Media
6. **Input malformati → 500** (`/api/login`, `/api/state`). `hmac.compare_digest` su `str` solleva eccezione con password non ASCII.
7. **Nessuna validazione server dello stato**: qualsiasi JSON con le 7 chiavi è accettato. Combinato con interpolazioni non escapate nel frontend (`weight`, `waist`, `duration`, `week`, `kg`, `reps`, valori `draft`) un backup manomesso può eseguire script (XSS). `video` accetta qualsiasi schema URL.
8. **Conflitto 409 non recuperabile**: dopo un 409 tutte le scritture successive falliscono finché non si ricarica, e ricaricando si perdono le modifiche locali.
9. **Login senza rate limit**; il token di sessione è costante (`'authorized'` firmato): il logout non lo invalida, l'unica revoca è ruotare `SESSION_SECRET`.
10. **Mobile: Impostazioni e Logout irraggiungibili** (sidebar nascosta < 750 px, bottom nav senza Impostazioni).
11. **Nessun header di sicurezza** (CSP, `X-Frame-Options`/`frame-ancestors`, `nosniff`, `Referrer-Policy`).
12. **Modello a blob unico**: ogni salvataggio riscrive tutto (limite 2 MB, raggiungibile in qualche anno di log), nessuna query, conflitti tra dispositivi su dati non correlati.

### Bassa
13. Frontend e CSS minificati senza sorgente: manutenzione difficile, diff illeggibili.
14. Settimana del programma manuale (c'è `startDate` ma non è usato).
15. Articoli spesa senza categoria non vengono mostrati (filtro `g.category===cat` vs `||'Altro'`).
16. Eliminazione pesata senza conferma; peso ≤ 0 scartato in silenzio.
17. Link video `b4` Leg extension: ID di 10 caratteri (`uM86QE59Tg`), troncato già nel PDF → probabilmente non funzionante, da verificare.
18. README non allineato: dichiara porta su `127.0.0.1` e volume `fitweek_data`; in realtà `192.168.222.200` e `fitweek-app_fitweek_data`.
19. Container in UTC (`TZ` non impostato): oggi irrilevante (date calcolate nel browser), rilevante appena il server calcolerà "oggi".
20. Dipendenze non bloccate in modo transitivo; immagine base non fissata a digest.

## Cosa funziona bene (da mantenere)

- Stack minimale, nessuna dipendenza cloud o CDN, avvio semplice.
- Container non root, healthcheck, segreti obbligatori e validati all'avvio.
- Cookie HttpOnly + SameSite=Lax + controllo Origin sulle scritture.
- Controllo di concorrenza ottimistico (versione).
- PDF servito solo dopo login.
- Testi prudenti su nutrizione e BPM, nessun dato fittizio spacciato per reale (prezzi marcati come stime).

## Valutazione stack

- **SQLite**: adeguato (un utente, pochi MB/anno). Nessun motivo per PostgreSQL.
- **FastAPI**: adeguato; va solo strutturato in moduli.
- **Frontend vanilla**: adeguato per dimensioni e per il requisito "niente build/CDN". Il problema è la minificazione e il monolite, non il framework. Raccomandazione in `DECISIONS.md` D-002.
