## New findings

### FW-REV-009 — P1 — Timestamp truncation defeats same-second offline deletion protection

- **File:** `app/workouts.py:39-51,225-246`.
- **Evidence:** `edit_time()` uses `isoformat(timespec='seconds')`, dropping milliseconds received from JavaScript. `is_stale` uses strict `saved > incoming`. Two edits within one second produce the same persisted timestamp even if their order differs.
- **Reproduction scenario:** a set DELETE is created at 12:49:10.900 and processed first, marking `set_tombstones` at `12:49:10`. A delayed prior PUT created at 12:49:10.100 then arrives; it is normalized to the same `12:49:10`, so `is_stale(tombstone, put)` returns false and the deleted set is recreated.
- **Impact:** user data reappears against intent; FW-REV-002 is not fully fixed. Similar collisions affect regular last-writer-wins edits made within the same second.
- **Fix:** preserve subsecond precision for both incoming edited timestamps and server-generated markers; define consistent tie behavior for truly identical timestamps (e.g., revision/sequence). Verify timezone and migrations for existing second-precision data.
- **Tests:** two edits in same second with distinct milliseconds delivered out of order; ensure earlier PUT cannot resurrect a later DELETE, plus test same-second updates of an existing set.
- **Evidence type:** deterministic source-level comparison, with isolated Python datetime demonstration. Not an application end-to-end run.

### FW-REV-010 — P2 — Logout can silently leave Android Keystore session valid

- **Files:** `static/js/logout.js:15-30`, `static/js/platform.js:60-73`.
- **Evidence:** signOut swallows a failed `/api/logout`; `setToken(null)` swallows `plugin.clear()` error and returns; signOut reloads as if successful. `initToken()` on next launch reads the still-persisted Keystore value.
- **Reproduction scenario:** Android device temporarily offline while Keystore clear fails; logout ignores both failures, reloads, then can restore the previous token from Keystore. The server session has not been revoked.
- **Impact:** a user believing they signed out may be reauthenticated on the device; security and UX risk under simultaneous failures. No evidence this occurred in production.
- **Fix:** do not report successful logout if local secure deletion failed. Confirm `clear()` success (or verify `get()` returns empty), display actionable error; on API revocation failure retain a pending-revoke state and prevent automatic reauthentication until resolved. Add mocked plugin/network test.
- **Tests:** simulate logout endpoint failure plus Keystore clear rejection, recreate module/app startup, assert no silent reauthentication/success indicator.
