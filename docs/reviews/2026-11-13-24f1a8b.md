## FW-REV-010 — persistent P2

### Correction verified
At `static/js/logout.js:56-66`, `signOut()` now captures the active token, calls `setToken(null)`, and, when revocation, secure wipe and both sign-out markers all fail, restores the token in memory with `keepToken()`, does not clear queue or local state, reports that sign-out did not complete and returns `false` without reloading.

For a token present in Keystore, this corrects the previously documented recovery-before-restart case. The targeted tests in `tests/js/logout.test.mjs` independently pass, including recovery of writable storage before restart and the separate server-revoked case.

### Residual defect confirmed
Evidence:
- `static/js/platform.js:115-131`: when Keystore migration fails, the legacy token intentionally remains in `fitweek.token.v1` and is used in memory.
- `static/js/platform.js:151-162`: every `setToken(null)` removes `TOKEN_KEY` before the wipe and marker outcome is known.
- `static/js/platform.js:176-180`: `keepToken()` restores only `memToken`; it cannot restore the pre-existing legacy persistent copy.
- `static/js/logout.js:56-61`: the incomplete path relies on `keepToken(held)` and tells the user that sign-out did not happen and device data was not deleted.

Independent reproduction:
1. A legacy token exists in `fitweek.token.v1` and Keystore migration fails.
2. Server revocation fails and the user confirms a device-only sign-out attempt.
3. Keystore wipe fails; `localStorage` cannot write a marker; the WebView cookie is rejected.
4. `signOut()` returns `false`, retains the token only in memory and displays "sei ancora collegato" / "Nulla è stato eliminato".
5. `fitweek.token.v1` has nevertheless been removed.
6. After storage becomes writable and the app restarts while Keystore remains unavailable, `initToken()` returns `null`.
7. The server session is still valid because revocation failed.

Classification: confirmed reliability/authentication-state defect, not a speculative vulnerability.

Impact:
- UI and persisted authentication state disagree.
- The user cannot rely on the promise that the unsuccessful operation left authentication unchanged.
- A valid server session can remain active after the device loses its only local token; direct revocation from that device then requires reauthentication.
- Queue and application data are not cleared in this path; the defect concerns the persistent authentication token and revocation workflow.

Required correction:
- Do not irrevocably remove the pre-existing legacy token until sign-out has a conclusive outcome, or provide a rollback that restores only a legacy token that already existed before the call.
- Do not copy a token that originated solely in Keystore into clear-text storage.
- Keep the current behavior for completed logout and server-revoked cases.

Required regression test:
- Start with legacy token plus failed Keystore migration.
- Fail server revocation, Keystore wipe, localStorage marker and cookie marker.
- Assert `signOut() === false`, local state remains intact, the same persistent legacy token remains available after restart, and a later successful retry revokes/clears it.
- Add the complementary server-revoked case to prove that completed logout still removes the legacy token.

No new FW-REV ID is created: this is a residual path of FW-REV-010 and directly intersects the existing FW-REV-005 migration concern.

## FW-UX-001 verification
`static/js/ui.js:4-52` now maintains a bounded collection of pending restore callbacks. Multiple removals extend the seven-second window, undo runs callbacks from last to first, and the final persistence/render callback runs once. `static/js/views/shopping.js` uses this helper for both shopping-list and pantry removals. A plain informational toast preserves an unexpired undo action.

Independent unit coverage passed for multiple removals, expiry, intervening informational notices, ordering, deduplication and list changes. Existing store tests also passed for in-flight persistence, 409 merge and two rapid removals. No engineering regression was confirmed.

Residual verification gap: Playwright was not executed, so touch behavior, visual wrapping and real browser timing remain unverified.

## FW-UX-002 verification
`static/js/ui.js:68-97` separates true `tablist`/`tab` controls from `radiogroup`/`radio` choices. Diary days, plan days, meal-template slots and reminder days now resolve to labelled tab panels. Theme and workout routine selectors use radio semantics. `static/js/main.js:173-191` applies keyboard navigation and post-render focus restoration to both patterns.

Unit tests passed for roving tabindex, disabled-day skipping, arrow/Home/End behavior, panel association and radio semantics. Static inspection found no missing panel in the changed renderers. No engineering regression was confirmed.

Residual verification gaps: the updated Playwright traversal, screen-reader behavior, responsive rendering and Android WebView compatibility were not executed. The wide-screen meal plan intentionally exposes all seven labelled panels; its UX interpretation remains under the UX reviewer, not this engineering Ledger.
